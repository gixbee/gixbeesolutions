# Critical Security Findings — 2026-07-13

Second audit pass (the first, `AUDIT_2026-07-13.md`, covered performance +
data-leak/race issues). This one is **security only**. Everything marked
**[FIXED]** was corrected in this pass; the **[YOU]** items need action from you
and cannot be fixed in code.

---

## 🔴 CRITICAL — exploitable without any login

### 1. [FIXED] Anyone could hire/reject/blacklist job applicants
`PATCH /hiring/applications/:id/status` had **no auth guard at all**. Any
anonymous caller could set any application to SELECTED, REJECTED or NO_SHOW —
and NO_SHOW also applies a permanent ranking penalty to that job-seeker.
→ Controller now JWT-guarded; only the job's **employer** can change status.

### 2. [FIXED] Anyone could take over any business
`POST /businesses/:id/operators` was **unauthenticated** — an attacker could add
themselves as an operator of any business and gain control of it. The calendar
endpoints (`add`/`remove` offline days) were open too.
→ JWT-guarded + owner-only checks.

### 3. [FIXED] Applicant PII harvesting
`GET /hiring/jobs/:id/applications` (unauthenticated) returned every applicant's
**résumé URL and cover letter** for any job id. `GET /hiring/jobs/:id/matches`
likewise exposed recommended candidates.
→ Both are now employer-only.

### 4. [FIXED] Booking OTP leak — the arrival/completion gates were bypassable
`GET /bookings/:id` and `GET /bookings/:id/status` returned **the arrival and
completion OTPs**, plus customer PII and the exact service address, to *any*
logged-in user for *any* booking id. The entire OTP security model (worker must
prove arrival, customer must confirm completion before payment) could be
defeated by reading the code from the API.
→ Both endpoints are now participant-only; the arrival OTP is returned **only to
the customer**. Same for `PATCH :id/status`, `:id/cancel`, `:id/confirm`,
`:id/refresh-completion-otp` — these previously let anyone complete or cancel
someone else's booking (and completion triggers wallet settlement).

### 5. [FIXED] Push-notification hijack
`PATCH /admin-user-list/:id/fcm-token` trusted the id in the URL — any user could
overwrite **another user's device token**, redirecting their push notifications
(including OTP pushes) to the attacker's phone.
→ Self-or-admin only.

### 6. [FIXED] Open phishing endpoint
`POST /notifications/test` (unauthenticated) sent an **arbitrary title/body push
to any device token** supplied by the caller. Combined with #5, a targeted
phishing push.
→ Endpoint removed; the whole notifications controller is now guarded.

### 7. [FIXED] Login-OTP handed out in the API response
`/auth/request-otp` returned the OTP in the JSON body whenever
`NODE_ENV !== 'production'` — and the checked-in `.env` sets
`NODE_ENV=development`. Any deploy that didn't explicitly override it would give
**anyone a full login bypass for any phone number**.
→ Now requires an explicit `ALLOW_OTP_ECHO=true` flag that no real deploy sets;
production also refuses to boot with it enabled.

### 8. [FIXED] Upload filter bypass → hostile file served from your API domain
The image check `.match(/\.(jpg|...)$/)` was **unanchored**, so `x.jpg.html`
passed, and the stored extension was taken from the user's filename. Uploads are
publicly served, so an attacker could host HTML/scripts on your API origin.
→ Extension whitelist is now anchored, MIME is validated, and the stored
extension is derived from the whitelist (never user input). SVG excluded.

## 🔴 CRITICAL — [YOU] cannot be fixed in code

### 9. Weak/known secrets in the deployed environment
`backend/.env` contains `JWT_SECRET=super-secret-key-for-gixbee` and
`ADMIN_USERNAME=admin` / `ADMIN_PASSWORD=admin`.

**Why this is the worst item on the list:** anyone who knows that JWT secret can
**forge a token claiming `role: ADMIN`** and walk past every admin guard — total
platform takeover, no password needed. The value is now also in this chat.

Good news: `.env` and `firebase-service-account.json` are **not** committed to
git (verified) — so this isn't public via the repo.

**Do now:**
1. Generate a strong secret: `openssl rand -base64 48` → set `JWT_SECRET`.
2. Set a real `ADMIN_USERNAME` and a long `ADMIN_PASSWORD` (12+ chars).
3. Rotate the **Firebase service-account key** (it's a live private key on disk).
4. Rotate the **Ola Maps key** (shared in a screenshot/chat).
5. Revoke the **old Google Maps key** (`AIzaSyB6PO…`) — it shipped in past APKs.

To help enforce this, the backend now **refuses to start in production** if
JWT_SECRET is default/short, admin creds are default, or OTP echo is on.

## 🟠 Remaining (medium — not exploitable for takeover)

- Any logged-in user can look up any user by UUID (`GET /admin-user-list/:id`,
  `/search`). Kept deliberately — the app's operator-picker uses it — and the
  serializer now strips tokens/balances. Tighten if it ever exposes more.
- When PhonePe/Razorpay go live, **wallet credits must be gated by a verified
  server-to-server signature**, never by a client call. (No such route exists
  today; the money paths themselves are sound and row-locked.)

## Verified OK (no action)
OTP generation/TTL/single-use, rate limits on OTP + admin login, refresh-token
hashing, wallet transfer locking, and rentals/addresses/favourites/messages/
support/talent scoping all check out.
