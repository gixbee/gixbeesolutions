Cloud

What the credits are for.

Gixbee is a live marketplace. Matching, maps, calls, and alerts only work if the service stays up while people are moving. Cloud capacity is the production system, not a demo environment.

Workloads

What runs in the cloud.

WorkloadRoleWhy it has to stay on
API Bookings, profiles, businesses, hiring, rentals, support. The Android and iOS apps call it throughout a job.
Realtime Live pro location, job offers, chat, and in-app call signaling. Those connections stay open for the length of a trip or a conversation.
PostgreSQL System of record for accounts, bookings, businesses, jobs, and rentals. Every confirm, cancel, and hire is stored here.
Redis One-time passwords, who is live, background queues, and realtime fan-out. Matching and login checks need a fast shared store across API instances.
Background workers Request timeouts, travel-progress checks, reminders, and notification dispatch. They run after the phone request has already returned.
File storage Profile photos and uploads. The apps fetch media separately from the database.
Staff console Web app for verification, disputes, support, and health. Operations staff use it while the public apps are in the field.

Compute

More than one API instance behind a load balancer, so a single process restart does not drop live jobs. Containers package the API and the staff console.

Data

PostgreSQL for records, with a connection pool in front of it. Redis for short-lived state. Object storage for photos and files.

Bandwidth

Map updates, photo loads, push fan-out, and voice signaling grow with the number of live jobs in Kerala and Tamil Nadu.

Stack

What the software is.

The mobile apps are Flutter. The API is implemented in TypeScript (NestJS) and in Rust; either one can serve the apps. The staff console is Angular. Data sits in PostgreSQL. Redis backs passwords, queues, and realtime. Payments in the app go through Razorpay. Login texts go through an SMS provider. Push uses Firebase Cloud Messaging. Maps use vector tiles for the live trip.

How usage grows the bill

A quiet hour still needs the database, cache, and at least one API process, because a pro can go live at any time. A busy hour adds open realtime connections, location updates, notification sends, and media. Credits cover that production capacity: virtual machines or containers, managed database, cache, storage, and outbound traffic.

How access is held

  • Phone login uses a one-time password stored briefly, then checked. The app keeps a signed session.
  • The staff console is a separate sign-in with page-level access, not the public app login.
  • Realtime rooms take identity from the signed session. A client cannot publish another person’s location by typing an id.
  • Production boot refuses placeholder payment and SMS secrets.
  • Ordinary API responses leave out wallet balances, push tokens, and other private fields.
